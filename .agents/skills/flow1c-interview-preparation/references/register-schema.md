# Структура реестра и прослеживаемость

## Основная таблица

По умолчанию используй эти колонки; существующий согласованный формат имеет приоритет.

| Колонка | Смысл |
|---|---|
| Код уровня 1 | Идентификатор блока |
| Процесс 1 уровня | Например, «Закупки» |
| Код уровня 2 | Идентификатор группы процессов |
| Процесс 2 уровня | Например, «Управление заказами поставщикам» |
| Код уровня 3 | Идентификатор операции или самостоятельного сценария |
| Процесс 3 уровня | Например, «Изменение и закрытие заказа поставщику» |
| Что уточняем на интервью | Текущее правило, желаемое правило, исключения и пример |
| Владелец процесса / правила | Кто утверждает порядок, ограничения и результат; роль, ФИО только если предоставлено |
| Исполнитель / участник интервью | Кто выполняет операцию и может показать практику |
| Ответ / решение | Ответ заказчика с датой/автором, если известны; не выдумывать |
| Требование / критерий приёмки | Согласованное правило и наблюдаемый результат проверки либо отметка «Требует согласования» |

Если роли пока неизвестны, пиши «Уточнить» или «Предполагаемый собеседник: …». Не выдавай рекомендованную роль за назначенного ответственного. Ответ и утверждённое требование до интервью можно оставить пустыми.

При небольшом реестре требования помещаются в последней колонке. При нескольких требованиях на вопрос или необходимости согласования создай отдельный лист «Требования»: ID требования, код L3, ID вопроса/ссылка на строку и версию реестра, исходный ответ, текст требования, критерий приёмки, статус согласования, владелец, приоритет, способ реализации, основание проверки. Ссылка только на номер строки менее устойчива, чем ID; при последующих обновлениях предпочтительнее ID.

Дополнительные колонки (ID вопроса, статус, приоритет, исходный номер вопроса, источник, система AS-IS/TO-BE) добавляй по необходимости. Для подробных ссылок можно использовать лист «Источники»: ID, URL/файл и раздел, тип источника, продукт/редакция/релиз, дата проверки, доступность, подтверждённый вывод, связанные процессы/вопросы. Список «Открытые вопросы» нужен, если есть отдельные решения вне самих интервью.

## Иерархия и коды

- Блок L1 — функциональная область. L2 — группа работ с общей целью. L3 — операция с различимым входом, результатом или правилом.
- Новая нумерация может выглядеть как `01` → `01.02` → `01.02.03`; храни коды текстом, чтобы Excel не менял ведущие нули. Уже существующую систему кодов сохраняй.
- В каждой строке повторяй все пары кода и названия. Не объединяй ячейки внутри таблицы, не заменяй повторения пустыми полями и не размещай заголовки групп отдельными строками посреди данных.
- Повтор одного кода L3 допустим для нескольких вопросов одного процесса. При этом его название и родители должны совпадать. Для уникальности строки используй ID вопроса, если он нужен.
- При расширении сначала сопоставь смысл со существующими процессами. Не создавай новый процесс только из-за другого вопроса и не меняй старые коды ради красивого порядка.
- Новый код выдавай после проверки на занятость. Изменение смысла или перенос процесса сопровождай таблицей соответствия; не разрушай ссылки на ответы и требования.

## Формулировки

Названия: «Учёт …», «Создание …», «Согласование …», «Планирование …», «Подбор …», «Приёмка …», «Блокировка …», «Управление …». Удали инфинитивы в начале названий L3 и цифровые префиксы из названий на всех уровнях.

Хороший вопрос: «Кто может изменить количество в согласованном заказе, нужна ли повторная проверка лимита и что происходит с уже оформленными поступлениями? Покажите пример изменения». Ответ определяет право, переход состояния, контроль и влияние на связанные документы.

Слабый вопрос: «Нужен ли заказ поставщику?» — не раскрывает механизм работы.

## Из ответа в требование

Пример исключительно для иллюстрации: заказчик согласовал минимальный остаточный срок годности на дату доставки покупателю.

- Бизнес-требование: при подборе серии учитывать дату доставки, норматив клиента и дату окончания срока годности.
- Открытые решения: единицы норматива (дни/процент), календарь и часовой пояс, источник даты доставки, изменение маршрута, исключения и права разрешения.
- Критерий: при известных датах серия, нарушающая согласованный норматив, не проходит выбранную контрольную операцию; подходящая серия проходит; изменение даты вызывает повторную проверку; разрешённое исключение фиксирует автора и основание.
- Способ реализации: «Требует проверки в целевом релизе», пока механизм не проверен.

Этот пример не устанавливает обязательное правило для всех клиентов и не обещает наличие соответствующей типовой функции.
