# Подготовка интервью и реестра процессов

Помоги пользователю подготовиться к обследованию заказчика. Результат — реестр
процессов, вопросов и требований в согласованных границах, а не каталог функций
1С. По умолчанию работай на русском, простым языком сотрудников заказчика.

## Маршрут и инструменты

Это единственный primary skill для этого сценария во всех клиентах. Начни
`flow1c_begin` / `scripts/flow1c.py agent-begin --json-stdin` с
`operation=interview-preparation`, `mode=draft`. Для обсуждения метода или
проверки книги без изменения используй `explore`. Не включай formal из-за
слова «требования» или номера задачи. Не требуй настроенной конфигурации,
RLM, формального реестра, номера разработки, шаблона и заполненной анкеты.

Проверь `doctor --json --operation interview-preparation`. Excel дополнительно
требует openpyxl из requirements.txt; установка зависимостей проходит через
согласованный bootstrap. Пока её нет, можно готовить Markdown через `flow1c_write`.
Для Markdown проверь `doctor --json --operation interview-preparation --format markdown`.
Не устанавливай ничего без согласия и не подключай профиль full.

Для XLSX используй `flow1c_interview` / `interview-register --json-stdin`:
`inspect` → `write` → `audit` → `flow1c_complete`. Контракт и примеры —
`docs/interview-preparation.md`. Прими выбранный пользователем существующий
файл/папку через `flow1c_intake`; source — только возвращённый относительный path.
В OpenCode справочники и контракт читай через `flow1c_inspect` scope=workflow;
не обходи gate через bash, edit, прямое чтение XLSX или webfetch.

## Вводные и источники

Используй уже сообщённые сведения. Уточняй только следующий существенный выбор:
целевой продукт и релиз, текущая система, блоки и границы интервью. Независимые
части готовь сразу; неизвестные значения отмечай «Уточнить». Анкета
[project-brief.md](assets/project-brief.md) необязательна. Сохраняй ответы через
`flow1c_dialogue`, не переспрашивай известное.

Зафиксируй заказчика, отрасль, партнёра и его роль, площадки, участников,
объёмы, проблемы и обмены. Сайт заказчика описывает продукцию и отрасль,
а не доказывает внутренний процесс. Кейс партнёра не означает согласованного
решения. Разделяй факт, гипотезу для интервью и открытое решение.

Для возможностей продукта приоритетны ИТС именно выбранного продукта/редакции/
релиза, затем официальные страницы 1С; для интеграций — документация поставщика.
Не переноси возможности между ERP, ERP УХ и УХ. Не предлагай доработку до
проверки типового механизма и бизнес-правила. При недоступном источнике сохрани
ограничение и продолжай бизнес-вопросы без обещания типовой поддержки. Не проси
пароли. Для закрытой ИТС используй предоставленный пользователем материал или
доступный авторизованный браузер; в клиенте без такого инструмента зафиксируй
«Требует проверки». Конкретные факты о подключённой конфигурации/расширении
требуют gated `flow1c_source_query`; общие бизнес-вопросы не требуют индекса.
Подробности: [sources-and-context.md](references/sources-and-context.md).

## Построение интервью

1. Прочитай [register-schema.md](references/register-schema.md). Сохраняй три
   уровня: блок L1, группа L2, операция/сценарий L3. Код и название — отдельные
   колонки каждого уровня; повторяй их в каждой строке. Названия L3 — через
   существительные («Учёт…», «Согласование…»), без цифровых префиксов.
   Основная колонка вопросов — «Что уточняем на интервью».
2. Для значимого сценария уточни триггер, входные данные, исполнителя, владельца
   правила, результат/документ и контроль. Где влияет на решение — объёмы,
   сроки, исключения, отмена/возврат, статусы, права, интеграции и отчётность.
   Различай AS-IS и TO-BE; проси практический пример без чувствительных данных.
3. Сохраняй формулировки и исходные номера вопросов пользователя. Разложенный
   вопрос связывай с исходным номером. Несколько вопросов одного процесса
   используют один код L3; ID вопроса — отдельная стабильная ссылка.
4. Выбирай глубину по значимости и разнообразию сценариев, без обязательного
   количества строк. Релевантные темы — [domain-map.md](references/domain-map.md),
   ЭДО/Диадок — [diadoc.md](references/diadoc.md). Смежные блоки включай только
   в части передачи данных и ответственности; не расширяй объём незаметно.

## Сохранение ответов и развитие реестра

Перед расширением прочитай актуальную книгу и ответы. Сопоставь смысл процессов
и родителей; переиспользуй их коды. Не перенумеровывай старые строки. Проверь
новые коды на занятость. Если нужен отдельный дополнительный реестр, используй
основной как контекст, включи только новые вопросы и укажи связь с его версией.
Дословные повторы проверяет инструмент; смысловые повторы проверяет агент.

Сохраняй исходный ответ в answer, нормализованное решение отдельно в decision.
Правки patches меняют только явно заданные поля ответа, владельца, участника,
решения, требования или источника. Не заменяй ответ предположением. Противоречия
выноси на согласование с указанием участников. Не выбирай сторону сам.

Требование из ответа описывает условие, действие/ограничение, результат и
проверяемый критерий. Связь с L3, ID вопроса и исходным ответом обязательна;
для неподтверждённых порогов/ролей пиши «Уточнить». Бизнес-правило и способ
реализации фиксируй раздельно. Метки реализации: «Типовой механизм подтверждён»
(только при evidence и проверке применимости), «Кандидат на настройку»,
«Кандидат на доработку», «Внешняя система», «Требует проверки».

draft_id — локальный идентификатор чернового требования; он не заменяет ID
из колонки J формального реестра. Вопрос без ответа не является требованием.
Новые требования имеют статус «Черновик» / «Требует согласования», вся книга —
UNVERIFIED_DRAFT. Не запускай registry-import для книги интервью. Формальная
привязка требует отдельно согласованного сопоставления с утверждённым реестром.

## Проверка и результат

Правила сохранности и оформления — [excel-rules.md](references/excel-rules.md).
Синяя шапка, белые строки, тонкие границы, перенос текста, текстовые коды,
без объединений. Таблица и все фильтры должны охватывать все строки и колонки.
Сохраняй ответы, коды, пользовательские колонки, комментарии, формулы, условия
фильтра и оформление. Адаптер отказывает книгам с неподдерживаемыми элементами,
сохраняя исходник; не обходи отказ с потерей элементов книги.

`flow1c_interview write` создаёт новую копию в каталоге draft текущего запроса
(во внешнем documentation_path или .workspace), перечитывает и проверяет XLSX.
Одинаковый запрос возобновляет тот же неизменённый результат. Исходники не
перезаписываются. Новую/переформатированную книгу дополнительно просмотри
визуально доступным инструментом таблиц; структурный audit не является такой
проверкой. Если просмотра нет, явно укажи ограничение.

Заверши `flow1c_complete` с output последней записанной книги либо Markdown-файла.
Выдай ссылку на файл, охват, новые темы, существенные открытые вопросы и
непроверенные ограничения. DRAFT_COMPLETE не означает утверждение требований
или готовность к публикации. Для explore заверши CONSULTATION_COMPLETE.
