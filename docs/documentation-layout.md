# Структура документации проекта

Новый проект создаёт четыре папки для исходных материалов и один служебный
каталог. Корневой README содержит назначения папок и ссылку на состояние проекта.

```text
Документация проекта/
├── README.md
├── Документы для анализа/
├── Материалы встреч/
├── Реестр процессов и требований/
├── Шаблоны документов/
└── .flow1c/
    ├── layout.json
    ├── inbox/
    ├── registry/
    ├── work-items/
    ├── drafts/
    ├── requests/
    ├── document-templates/
    ├── wiki/
    └── .workspace/
```

Области создаются по мере использования; configure создаёт начальные инструкции,
а хранилища добавляют свои файлы при выполнении операций. Имя `.flow1c` обозначает
назначение каталога, но не гарантирует его скрытие в Проводнике Windows.
Агент возвращает конкретную ссылку на результат. Исходные материалы остаются
в пользовательских папках; помещение файла в них само по себе не запускает
импорт или анализ.

## Версии и совместимость

Версия хранится в `.flow1c/layout.json` по
`schemas/documentation-layout.schema.json`: `schema_version=1`,
`layout_version=2` для новой структуры. При отсутствии записи или явном
`layout_version=1` служебные области находятся непосредственно в корне
документации. Неизвестная или повреждённая версия отклоняется без перезаписи.
Наличие одной папки `.flow1c` не включает новую структуру.

Новую структуру выбирает configure для пустого каталога (допускается `.git`).
Существующий непустой каталог либо уже подключённый проект без записи версии
сохраняет прежнее расположение. Запись версии сохраняется перед созданием
инструкций: после прерывания повторный configure продолжает тот же layout.
Пользовательские README и документы, включая пустые файлы, не заменяются.
Конфликты путей, symlinks и junctions проверяются до создания scaffold.

`template configure` создаёт такой же scaffold для нового каталога документации,
не требуя Git или полной настройки проекта. Существующая библиотека сохраняется.
Явный перенос библиотеки в другой каталог учитывает layout назначения и оставляет
старую копию; он не переносит остальные данные проекта.

Update сохраняет версию структуры, пользовательские данные и незавершённые
операции. Автоматической миграции существующего проекта в layout 2 нет.
Ручное перемещение папок или изменение layout.json не является миграцией:
сохранённые абсолютные пути, hashes и sealed records требуют отдельного
контракта переноса с backup и resume. Продолжайте использовать прежний layout
до появления такой операции.

## Контракты путей

- `documentation_path` остаётся корнем репозитория документации, пользовательских
  материалов и Git. `.git` находится в этом корне.
- `flow1c.context.project_data_root` возвращает корень служебных данных:
  documentation_path для layout 1, documentation_path/.flow1c для layout 2.
- Persisted относительные ссылки intake остаются относительно documentation_path:
  например, `.flow1c/work-items/G-001/input/meetings/...` для layout 2.
  Ссылки разделов внутри work-item и request остаются относительно их владельца.
- Git commit вычисляет pathspecs относительно репозитория, включая префикс
  `.flow1c` при layout 2. Проверки посторонних staged files и условия публикации
  сохраняются; весь служебный каталог не становится разрешённым для commit.
- Runtime установки Flow1C (`.workspace`, `.venv`, `.tools`) остаётся в checkout
  продукта. Под `.flow1c/.workspace` сохраняются только служебные данные
  документации, например DOCX plans.

Чистая политика версий и шаблонных проекций принадлежит
`flow1c.documentation_policy`; чтение layout и создание scaffold —
`flow1c.documentation`. PowerShell вызывает этот сервис через отдельный
запускатель, без повторной реализации правил путей.
