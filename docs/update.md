# Обновление Flow1C

## Обычный сценарий

После первичной настройки пользователь просит агента OpenCode обновить Workflow или запускает `/update`. Повторно вводить локальные пути и URL не требуется: они хранятся в игнорируемом `.flow1c.local.json` и проходят автоматическую проверку.

В OpenCode команда `/update` открывает формальный update gate и вызывает `flow1c_action action=update`. Этот инструмент запускает из корня репозитория:

```powershell
PowerShell -ExecutionPolicy Bypass -File .\scripts\update.ps1 -Json
```

Обновлятор выполняет только fast-forward текущей ветки Workflow до настроенного upstream. Перед изменением он проверяет отслеживаемые файлы и сохраняет локальный конфиг вместе с предыдущим Git-коммитом в `.workspace/backups/update-<timestamp>-<update_id>/`. Если `extension_mode` равен `git`, он также загружает изменения настроенного репозитория расширения и выполняет fast-forward его текущей ветки до upstream. URL удалённого репозитория должен совпадать с `extension_repository_url`; локальные изменения, detached HEAD и расхождение истории блокируют обновление расширения. Для `local-export` Git-обновление пропускается.

После получения новой версии обновлятор:

1. мигрирует `.flow1c.local.json` до актуальной схемы, сохраняя неизвестные пользовательские поля;
2. валидирует `config/external-tools.json` и снимает версии/commit-ы `rlm-tools-bsl`, `cc-1c-skills` и BSL Language Server;
3. при разрешённой политике безопасно применяет обновления, сохраняя старые версии и snapshot в каталоге backup;
4. запускает локальный RLM MCP, проверяет `/health`, строит отсутствующие индексы и обновляет существующие отдельными сохраняемыми заданиями RLM; после fast-forward расширения обновление его индекса запускается один раз для этого `update_id`, даже если предыдущая проверка ещё показывает `FRESH`;
5. выполняет проверки RLM и индексов, затем `scripts/flow1c.py doctor --json --profile project-basic`. Этот профиль проверяет базовую готовность проекта; отдельные проверки MCP-сессии выполняются полным `doctor --json`.

Вывод `update.ps1` сохраняется во временных файлах на время действия `flow1c_action`, поэтому фоновый RLM не удерживает ответ инструмента после завершения PowerShell. Длинная индексация возвращает `WAITING_BACKGROUND`, `ready:false`, `update_id`, `checkpoint_path` и `jobs`. Это обычное ожидание: Git-файлы уже могут быть обновлены, но готовность ещё не подтверждена. Агент продолжает тот же `gate_id` через `flow1c_action action=update` с `{"confirmed":true,"wait_seconds":30}`. CLI автоматически сохраняет ID обновления и ранее разрешённые опции; новый gate и повторное согласие для продолжения не нужны.

При ручном запуске продолжайте ID из JSON:

```powershell
PowerShell -ExecutionPolicy Bypass -File .\scripts\update.ps1 -Json -UpdateId <ID-из-результата> -WaitSeconds 30
```

Каждый вызов ждёт фоновые задания до 30 секунд суммарно. Если они ещё выполняются, вернётся то же `WAITING_BACKGROUND`; повторный вызов использует существующие PID/задания. Перед возобновлением проверяется неизменность локальной конфигурации и HEAD Workflow. При их изменении нужно начать новый update без `-UpdateId` (в CLI: `new_run:true`); пользовательские изменения и прежний backup сохраняются. Перезапуск OpenCode допускается между вызовами — ID записаны на диске. В новых адаптерах разрешено завершить уже авторизованный индексный checkpoint после изменения файлов адаптера; для других инструментов по-прежнему нужен полный перезапуск OpenCode после успешного update. Старый адаптер может потребовать перезапуск раньше: продолжайте сохранённый gate/update_id после него.

JSON обновления остаётся schema 2: добавлены поля `update_id`, `phase`, `checkpoint_path`, `jobs`, `options`; `READY` и `ready:true` сохраняют прежнее значение. Потребитель должен проверять их, а не только exit code 0. Update checkpoints и читаемый прогресс находятся в `.workspace/updates/`; полная история этапов записана в `<update_id>.events.jsonl`. Ответ во время ожидания содержит только последние четыре этапа, чтобы длинная индексация не раздувала контекст агента. Одновременные синхронные update-вызовы в одном checkout блокируются. Старые index job schema 1 принимаются: живое задание не запускается повторно, а старые записи и журналы сохраняются при создании нового задания schema 2.

## Свежесть индекса и диагностика

В RLM 1.41/1.42 полный `index update` без изменений BSL может оставить прежний `built_at`; спустя семь дней следующий `index info` снова сообщает `stale (age)`. Flow1C не редактирует базу RLM и не меняет системный лимит возраста. После успешного задания он выполняет строгую проверку структуры/содержимого, временно исключив только календарный предел в этом дочернем вызове. Подтверждение сохраняется в `.workspace/rlm-index/<source_id>/validation.json`: совпадают снимки файлов до/после, идентичность базы и версия RLM. Оно действует не дольше `RLM_INDEX_MAX_AGE_DAYS` (по умолчанию семь дней). Смена файла/пути/размера/mtime/ctime, включая XML, базы, версии или истечение срока отменяет подтверждение; doctor и обновлятор используют общий Python-контракт. Это проверка неизменности файлов по атрибутам, а не криптографическая проверка содержимого каждого исходника.

Задание schema 2 хранит PID с временем создания, heartbeat, exit code и пути stdout/stderr; история прежних заданий остаётся в `history/`. Пока процесс жив, статус не запускает тяжёлый `index info`. Worker работает независимо от OpenCode и имеет предел один час; при превышении останавливается только принадлежащее ему дерево процессов, результат становится `FAILED`, база и журналы сохраняются. Незавершённое или ошибочное задание никогда не выдаёт подтверждение свежести.

После `FAILED` или `RECOVERY_REQUIRED` сначала прочитайте detail/журналы и исправьте причину. Безусловные повторные попытки блокируются. Для повторной попытки с сохранением истории используйте `-RetryFailedIndexes` вместе с `-UpdateId`, или `retry_failed_indexes:true` в `flow1c_action`; отдельный источник поддерживает `rlm-index.ps1 -Action Ensure -SourcePath <путь> -RetryFailed -Json`. Настройки, резервные копии и источники не удаляются. Тайм-аут 600 секунд остаётся защитой синхронных этапов Git/зависимостей/doctor; он больше не служит пределом всей фоновой индексации.

Автономная проверка без сети и рабочих источников: `python scripts/update-smoke.py --output .workspace/update-smoke-evidence.json`. Она создаёт новый локальный Git-клон и venv, проверяет PowerShell 5.1, миграцию, два фоновых источника, возобновление, сохранение backup и повторный update. RLM, HTTP-сервис и проверка внешних инструментов здесь синтетические; это проверка контракта обновлятора, а не подтверждение доступности конкретной рабочей конфигурации.

Совместимость установленного RLM CLI дополнительно проверяется через `python scripts/index-compat-smoke.py --output .workspace/index-compat-evidence.json`. Этот тест строит крошечный синтетический источник в отдельном временном кеше, воспроизводит старый возраст, проверяет обновление без дельты и отмену подтверждения после изменения XML. Пользовательские источники, сервис и рабочая база индекса не используются.

Проверить инструменты без изменения файлов:

```powershell
PowerShell -ExecutionPolicy Bypass -File .\scripts\update.ps1 -Json -CheckExternalToolsOnly
```

Чтобы применить совместимые кандидаты, используйте `-AllowExternalUpdates`. `-SkipExternalToolUpdates` предназначен только для аварийной диагностики и явно оставляет состояние `SKIPPED` в JSON. Без разрешения найденная новая версия возвращается как `UPDATE_AVAILABLE`, а не как `READY`.

Параметры агента `allow_external_updates`/`allowExternalUpdates` и `skip_external_tool_updates`/`skipExternalToolUpdates` передаются в эти PowerShell-флаги без изменения manifest. Поэтому разовое согласие не требует редактировать `policy.apply_updates`.

`cc-1c-skills` обновляется только fast-forward-ом; локальные изменения и divergence блокируют операцию. BSL Language Server устанавливается в отдельный versioned-каталог только после SHA-256 и smoke-проверки. Плавающая ветка skills и применение новых версий по умолчанию не считаются предварительно утверждёнными: в manifest установлено `policy.apply_updates: false`.

Результат `READY` подтверждает проверки установки. Дополнительное поле
`agent_runtime.restart_required=true` означает, что обновились файлы `.opencode`
или `opencode.json`: после завершения успешного update gate полностью закройте
и откройте OpenCode с тем же проектом. Это перезагрузит набор инструментов и
разрешения; сохранённые gate, setup checkpoint и операции шаблонов остаются
доступными. До этого новые инструменты могут отсутствовать, даже когда CLI
показывает их в `available_actions`. `agent_runtime.state=UNCHANGED` означает
только отсутствие изменений адаптера в этом запуске, а не проверку живой сессии.
Обычное обновление не запускает `/setup` и не требует повторного подтверждения
сохранённых настроек.

После `READY` агент завершает формальный gate через `flow1c_complete` без поля `output`: для операции update выходной файл не предусмотрен. Ошибочный аргумент `output` возвращает исправимую ошибку и сохраняет gate открытым. Gate, который прежняя версия закрыла как `NON_COMPLIANT` исключительно из-за этого аргумента после успешного `flow1c_action update`, можно завершить повторным `flow1c_complete` без `output`; другие нарушения целостности остаются терминальными.

Если PowerShell-компонент выдал информационную строку перед JSON апдейтера, `flow1c_action` распознаёт этот совместимый формат и записывает успешное действие в gate. Отсутствие записи `action_completed` возвращается как исправимая ошибка завершения. Для gate, ранее закрытого как `NON_COMPLIANT` только из-за отсутствия этой записи, повторите `flow1c_action action=update` в том же gate и затем `flow1c_complete` без `output`. Обновлятор повторно проверит состояние и сохранит новый бэкап; новая настройка проекта не требуется.

Если после fast-forward требуется Python `>=3.10`, а текущая `.venv` отсутствует или несовместима, обновлятор возвращает `NEEDS_CONFIRMATION` и машинный `next_actions`. Верхней границы поддерживаемой версии нет. После одного согласия повторный запуск с `-RepairPrerequisites` устанавливает предпочтительный Python 3.14 через WinGet (либо использует указанный ранее одобренный offline-установщик), переносит старую `.venv` в `.workspace/backups/venv-repair-<timestamp>/`, создаёт совместимую среду и продолжает тот же update. Перезапуск терминала и отдельный `/setup` не требуются.

## Когда обновление блокируется

Обновлятор ничего не сливает автоматически и останавливается, если:

- `.flow1c.local.json` отсутствует, повреждён или имеет более новую неподдерживаемую схему;
- в отслеживаемых файлах Workflow есть локальные изменения;
- текущая ветка не имеет upstream, находится в detached HEAD или содержит собственные коммиты поверх upstream;
- Git не может выполнить fast-forward;
- Git-репозиторий расширения имеет локальные изменения, другую удалённую ссылку, не имеет upstream или разошёлся с ним;
- новая зависимость не установилась;
- manifest внешних инструментов невалиден, источник недоступен, checksum не совпал;
- в `cc-1c-skills` есть локальные изменения или история разошлась;
- smoke-проверка RLM, skills или BSL Language Server завершилась ошибкой;
- итоговый `doctor` не вернул `READY`.

В этих случаях агент сообщает точную причину. Он не выполняет `git reset`, не удаляет локальные изменения и не подменяет конфигурацию значениями по умолчанию. Повторный `/setup` нужен только для восстановления отсутствующей или невалидной конфигурации либо когда новая версия требует нового обязательного пользовательского значения.

## Версии и миграции

Версия поставки хранится в `VERSION`; опубликованные стабильные версии должны иметь соответствующие Git-теги `vMAJOR.MINOR.PATCH`. Схема локального конфига задаётся верхнеуровневым `schema_version`. Миграции последовательны, идемпотентны и выполняются скриптом `scripts/migrate-local-config.py` через атомарную замену файла.
## Git evidence migration

The update is backward compatible. Existing gates without `git_context` receive safe defaults at use time. Evidence schema v1 is read and normalized to v2; `NOT_MERGED` becomes `NO_INTEGRATION_EVIDENCE` while retaining `legacy_status`, and `NO_MERGE_COMMIT` becomes `FAST_FORWARD`. Existing action names remain accepted. Local configuration, request evidence and `.workspace/git-analysis` data are preserved; TTL cleanup is a separate explicit maintenance operation and never runs as a side effect of analysis.
## Сохранность пользовательских шаблонов

Библиотека находится в пользовательской документации вне checkout и не заменяется
при обычном update. Source/profile/guide, active/default и pins сохраняются.
Миграция локальной конфигурации 1→2 добавляет template_library, делает backup
и сохраняет неизвестные поля и functional_spec_template. Мигратор не выполняет
семантический разбор DOCX и не объявляет шаблон готовым. Предложите отдельный
импорт legacy файла через общий [контракт библиотеки](document-templates.md).
Просьба «обнови шаблон» направляется в template-management, а не Workflow update.
