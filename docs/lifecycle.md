# Жизненный цикл ФС

Независимые консультации и черновики предшествуют этому формальному циклу и не требуют идентификатора задачи. Их завершение не меняет статусы ниже; см. [диалог и черновики](dialogue.md).

## Статусы

```text
registered
  → clarification
  → specification_draft
  → functional_review
  → technical_review
  → ready_for_development
  → development
  → code_review
  → analyst_testing
  → acceptance
  → done
```

Если после разработки аналитик меняет утверждённую ФС, она повторно проходит функциональное и техническое согласование.

## Ветки

| Репозиторий | Этап | Ветка |
|---|---|---|
| Документация | новая ФС | `fs/<safe-reference-slug>/specification` |
| Расширение | разработка | `feature/<safe-reference-slug>` |
| Документация | уточнение после кода | `fs/<safe-reference-slug>/post-development` |
| Документация | тесты и сдача | `fs/<safe-reference-slug>/acceptance` |

Каждая ветка создаётся от актуальной `origin/main` и завершается PR. Статус на `main` отражает только слитые и утверждённые решения. Незавершённые PR добавляются к статусу при запросе Gitea.

## Изменение Excel

Один коммит импорта содержит:

- новую версию `registry/source/requirements.xlsx`;
- обновлённые нормализованные индексы;
- `registry/import-report.md` с добавленными, изменёнными и исчезнувшими строками;
- анализ влияния на существующие рабочие элементы.

Автоматический PR для затронутой ФС не создаётся. Агент показывает влияние и ждёт команды пользователя.

## Частично готовый реестр

Локальные ошибки строк и связей дают реестру статус `partial`, а не делают недоступными все корректные записи. Частичный индекс хранится отдельно от последнего полностью проверенного `normalized/`. Работа может начинаться по номеру ФС либо ID требования: для номера ФС нужна хотя бы одна ссылка на реально существующее требование, для требования — хотя бы один назначенный номер ФС. Посторонние ошибки не блокируют scoped snapshot. Несколько назначенных ФС или совпадение значения с ID требования и номером ФС требуют явного выбора пользователя. Структурные ошибки книги сохраняют статус `invalid` и блокируют использование файла.

## Provisional lifecycle

Work-item может иметь `traceability_mode: registry` или `provisional`. В provisional основанием служит `input/user-brief.md`; gate документных этапов завершается как `COMPLETE_WITH_DEVIATIONS`, `ready` остаётся `false`, а документы получают watermark `UNVERIFIED_DRAFT`. Публикация, изменение расширения и обычный `COMPLETE` запрещены до восстановления валидированной трассируемости.

`registry-reconcile` валидирует исправленный XLSX обычным импортёром, сохраняет отчёт и mapping, но применяет только точные или явно подтверждённые соответствия. При спорных соответствиях work-item остаётся provisional. После успешного reconcile старые evidence сохраняются и получают `revalidation_required: true`.
