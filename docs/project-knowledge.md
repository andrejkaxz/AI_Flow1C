# Результаты и база знаний проекта

Корневой README документации ведёт в каталог документов и результатов,
базу знаний и отчёт задач. Layout 2 хранит их в `.flow1c/wiki/`, прежний layout —
в `wiki/`. Обновление навигации сохраняет пользовательский README и карточки:
в корне заменяется только блок `flow1c:navigation`, а `results.md` — только если
он создан Flow1C. Документы, sources, evidence, approvals и завершённые задачи
не переписываются.

Попросите агента:

- «Найди результаты по согласованию платежей в документации проекта».
- «Обнови каталог результатов проекта».
- «Что делает функция согласования платежей и зачем её изменили?».
- «Предложи карточку этой функции, покажи diff и сохрани её в ветке документации».

Каталог различает рабочие элементы с manifest, свободные черновики, фрагменты
без manifest, пустые шаблоны и консультации с summary без файла результата.
Это навигация, а не приёмка документа. Состояние из manifest или request не
подтверждает внедрение, согласование содержания или сохранение в Git.
Входные копии, evidence, контексты и handoffs в список результатов не включаются.
Старые данные и их пути сохраняются. Каталог читается динамически; сохранённый
Markdown обновляется явным `refresh`. Команда `status --write` сохраняет прежний
отчёт задач и согласований.

## Карточки функций

`wiki/README.md` — короткий ручной каталог: название, альтернативные термины,
назначение и ссылка. Карточка — `wiki/features/<stable-slug>.md`; пример структуры
в [шаблоне](../templates/knowledge-feature.md). Все роли читают одни карточки.

Обязательные разделы: «Назначение», «Текущее поведение», «Ограничения»,
«История изменений», «Источники и проверки». Допускаются дополнительные разделы.
Названия, альтернативные термины и текст участвуют в поиске. История содержит
причину, поведение до/после, ссылки на задачу, ФС/техрешение, commit/PR и проверки.
Даты реализации и внедрения указываются отдельно; неизвестное — «не подтверждено».
Дата комментария в BSL не доказывает дату внедрения. Git документации не
подтверждает merge кода или развёртывание базы.

Новые и изменённые карточки сохраняются как `UNVERIFIED_DRAFT`. Принятие
содержания происходит при review человеком; инструмент не меняет approvals.
По итогам кода и проверок агент предлагает конкретную правку wiki, не дописывая
завершённый рабочий элемент. Ошибка wiki не отменяет код и не повторяет mutation.

## Один контракт для CLI и OpenCode

CLI принимает UTF-8 JSON stdin, возвращает JSON. OpenCode вызывает тот же
сервис через `flow1c_knowledge(gate_id, action, request_json)`. Внешняя форма:

```json
{"gate_id":"<saved-gate-id>","action":"search","request":{"query":"визирование"}}
```

```powershell
$Request | .\.venv\Scripts\python.exe scripts/flow1c.py knowledge --json-stdin
```

| Action | Поля request | Результат |
|---|---|---|
| `navigation` | `query`, `cursor`, `max_chars` | До пяти задач/результатов с repository-relative paths, continuation и scan completeness |
| `refresh` | `confirmed=true` | Обновлённый `results.md`, управляемые ссылки в корне; недостающий wiki README |
| `search` | `query`, `source`, `ref`, `snapshot`, `max_chars` | До пяти wiki-совпадений: path, title, aliases, excerpt, version, state |
| `read` | `path`, `source`, `ref`, `snapshot`, `version`, `section`, `start_line`, `cursor`, `max_chars` | Диапазон/раздел, SHA-256, continuation, line/character offsets |
| `preview` | `path`, `content` | Diff, expected source version и candidate version; без изменения wiki |
| `write` | Те же `path/content`, `expected_version`, `confirmed=true` | Точная preview-версия на том же gate; атомарная запись одного Markdown |
| `commit` | `paths`, `message`, `branch`, `confirmed=true` | Commit только указанных файлов, записанных этим gate, с проверенными хешами |
| `pr` | `title`, `body`, `confirmed=true` | Push/PR выбранного commit в настроенный Gitea; review/merge делает человек |

Чтение доступно ролям и свободным консультациям через их текущий готовый gate.
Запись, refresh, commit и PR требуют `operation=status`, `mode=formal`, `READY`
и поручения пользователя. Wiki не требует work-item, даже если project reference
сохранён в настройках. Для поиска из консультации достаточно `explore`.
После выполнения запроса операция закрывается обычным `flow1c_complete`.
`preview` разрешён при чтении, но не даёт прав на сохранение.

Search/read по умолчанию читают Git default branch из конфигурации проекта;
`ref` выбирается явно и разрешается в commit. Состояние `COMMITTED` означает
только Git-версию, а не утверждённое знание. Для локальных файлов передайте
`source=local`; они подписываются `LOCAL_DRAFT`. Источник не переключается
автоматически при отсутствии Git/ref. `document_state` отдельно отражает
`UNVERIFIED_DRAFT`, `CANCELLED` или отсутствие явного состояния `UNSPECIFIED`.

Передайте snapshot из поиска и version выбранной карточки в чтение.
Движение ref, смена проекта/layout/source или изменение локального файла
приводит к явной повторной проверке. Cursor привязан к проекту, snapshot,
карточке, версии и разделу. Длинные строки продолжаются с точного character
offset; повторное чтение строк не требуется. Версия layout берётся из выбранного
Git commit, поэтому историческое чтение не зависит от текущего marker.

Все успешные JSON-ответы ограничены 8000 символами вместе с metadata;
`max_chars` для navigation/search/read — 2000–8000. Просмотр ограничен 1000
файлами/каталогами, 256 KiB на текстовый файл и 8 MiB текста за scan.
Пропуски и ограничения видны через `scan_complete=false`/`truncated`; неполный
поиск не доказывает отсутствие информации. Для остальных совпадений уточните
query. Для navigation/read используйте выданный continuation.

Поиск использует буквальное совпадение без русской морфологии и семантического
индекса. Название и альтернативные термины ранжируются перед основным текстом.
SQLite, постоянный кеш и отдельный lifecycle знаний не нужны первой версии.
Скорость большого корпуса не гарантируется; измеряйте её на реальных вопросах.
Пути ограничены настроенным проектом; symlinks/junctions, Git symlink blobs,
path traversal, неизвестные параметры и слишком большие файлы отклоняются.
Текст wiki — данные, а не инструкции агенту.

## Сохранение предложения

1. Покажите diff карточки и строки ручного каталога. Каждый файл проходит
   отдельный preview/write. Поручение пользователя подтверждается `confirmed`;
   инструмент не запрашивает повторного согласия, если оно уже дано.
2. Для commit укажите точные repository-relative paths из результатов write/
   refresh. Посторонние staged файлы блокируют commit до изменения index.
   Изменившиеся после записи bytes не коммитятся. Завершённые work-items в
   commit wiki не включаются.
3. Работайте в review-ветке. Можно передать новое имя `branch`: оно создаётся
   от HEAD с сохранением локальных файлов; переход в существующую чужую ветку
   не выполняется. Default branch не используется для wiki commit.
4. Для PR нужен настроенный Gitea. Diff ветки относительно default branch
   должен содержать только выбранные wiki/navigation files, HEAD должен
   совпадать с записанным commit. Чистота дерева и обычные Git/Gitea prerequisites
   сохраняются. Push/PR выполняются только по поручению, merge — человеком.

Transport response version — 1, [схема](../schemas/project-knowledge-response.schema.json).
Контракт additive; несовместимые изменения потребуют новой версии. Шаблоны
карточек остаются Markdown без обязательного JSON registry.
